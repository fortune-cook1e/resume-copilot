# Resume Copilot 产品定义

状态：产品定义阶段。核心产品方向已确认；首版细节与验收范围待进一步收敛。

本文以本轮产品讨论为依据，描述重构目标，不代表现有代码已经实现。旧项目文档与实现不作为新版需求的约束。技术选型、架构和实施阶段拆分不在本文中决定。

## 1. 产品定位与痛点

面向需要为不同岗位准备简历的求职者，建立可复用的个人真实经历库，通过 Agent 协作或手动编辑生成不同岗位的简历。

典型场景：用户已有 frontend 简历，也希望投递 full-stack 岗位。教育、工作、项目等事实重复，但每次都要复制内容、重新解释经历并调整重点。

核心价值不是用聊天框替代表单，而是让用户不必反复提供相同事实，并能控制针对不同岗位的内容表达。

## 2. 三类核心信息

- **个人经历库**：跨简历复用的已确认事实，包括教育、工作、项目、职责、行动、技术和成果。可比简历中的表达更完整，不要求一次补齐或每条都有量化结果。
- **目标岗位**：用户提供的岗位方向、职位描述（JD）或职位链接。没有具体 JD 也能创建通用岗位简历。
- **岗位简历**：根据经历与目标选材、排序和改写形成的独立内容，支持手动编辑、排版、预览与 PDF 导出。

以上为产品概念，不是已经选定的数据表或存储结构。

## 3. 已确认的用户体验

### 3.1 首页与统一创建入口

- 用户进入应用后的首页展示简历列表，突出「根据岗位创建」能力；这里不指对外宣传页。
- 使用一个「创建简历」入口，而不是按岗位方向、JD、URL 拆成三个入口。
- 进入后，chat 可以询问：「你想创建什么样的简历？可以告诉我岗位方向、粘贴职位描述或发送职位链接。」
- Agent 根据输入理解创建意图。用户也可以不使用 chat，直接进入表单填写。
- 具体 JD 对应职位定制版；只有岗位方向时生成通用版，不能把通用预期说成特定公司的要求。

### 3.2 建立个人经历库

提供两种起步方式，最终汇入同一份经历库：

1. 导入已有简历，提取事实供用户核对。
2. 直接对话，由 Agent 采访、整理事实。

用户能够直接查看、编辑经历库，它不是隐藏的 AI memory。

Agent 提取的新增或更正事实集中展示在确认卡中，允许修改后一键保存；不逐句打断。未经确认的推断不能作为事实用于简历。

### 3.3 按目标生成简历

- 根据目标和经历库，先提出少量影响选材的关键问题，再生成草稿。
- 允许跳过问题；已有事实不反复询问，也不要求先完成整个经历库。
- 从经历库重新选择内容、调整顺序和篇幅，不局限于给旧简历替换关键词。
- 区分「没有记录」和「没有做过」：缺少重要事实时追问，不能按岗位要求补造经历、技能、贡献或数字。
- 创建新简历时直接生成可编辑草稿，不要求逐条批准草稿文字；其事实依据仍需确认。

### 3.4 适合笔记本的编辑工作台

两种可切换视图，共享同一份简历：

| 视图 | 操作区 | 预览区 |
| --- | --- | --- |
| Agent 协作 | Chat、事实确认卡、修改建议 | 简历实时预览 |
| 手动编辑 | Form、排版设置 | 简历实时预览 |

- 不强制同时展示 chat、form 和预览三个区域。
- 切换视图不创建副本、不清空聊天、不丢失编辑内容。
- 用户可随时选择手动填写，再让 Agent 基于最新内容继续协作。
- 产品内提供模板选择、排版与 PDF 导出，不要求用户搬运到外部编辑器。

## 4. 内容控制与数据边界

### 已有简历的 Agent 修改

- 展示修改前后内容，让用户接受或拒绝，不悄悄覆盖。
- 若用户在表单中修改了建议涉及的内容，该旧建议不能直接应用。
- 再使用时，应基于最新内容重新提出建议，避免覆盖用户的新修改。
- 撤销能力、差异展示粒度与确认卡具体 UI 尚需细化。

### 经历库与简历之间

- 简历措辞调整默认只影响当前简历，不自动回写经历库。
- 涉及新增或更正事实时，询问是否同步到经历库。
- 经历库变更不自动改动其他已经生成的简历。
- 用户直接编辑经历库与 Agent 提取待确认事实，是两条不同的操作路径；实现需保留这一区别。

## 5. 首版产品范围

已确认需要围绕以下能力形成闭环：

- 可维护的个人经历库，支持导入与对话建立。
- 统一创建入口，接受岗位方向、JD 文本、职位 URL。
- 针对性追问与事实确认。
- 岗位简历生成、Agent 修改确认、表单编辑。
- 简历列表、模板选择、实时预览、基础排版与 PDF 导出。

不以复刻 Reactive Resume 全部能力为目标。不要求首版提供大量模板或穷尽所有高级设置。

这是产品范围共识，不是一次性实施任务清单。每个实施阶段仍需定义可验证的最小交付。

## 7. 待确认项与建议（不是已采纳需求）

- URL 读取失败、需要登录或页面失效时的降级体验；建议提示粘贴正文，不猜测内容。
- 是否在生成前核对读取到的岗位摘要，以及是否保留 JD 内容快照与来源。
- 再次投递相似职位时的新建、复制、参考已有简历的具体规则。此前讨论未得到最终确认。
- 首批模板及基础排版设置范围；导入支持的文件格式。
- 登录时机、数据删除与保留、旧用户数据是否迁移。
- 极窄屏交互、生成中断与恢复等异常流程。
- 首版交付优先级及完整验收标准，需在实现前进一步明确；下方场景是已确认行为的整理，不代表完整验收清单。

## 8. 核心用户旅程

### 场景 A：已有 frontend 简历，希望投递 full-stack

1. 导入已有简历，核对并保存提取出的个人事实。
2. 点击「创建简历」，在 chat 中提供 full-stack 岗位方向、JD 或 URL。
3. Agent 根据已知经历，追问会影响内容选择的缺失事实，例如是否实际参与 API 开发。
4. 用户集中确认新事实；跳过的问题不被补造成经历。
5. Agent 从经历库选材，生成 full-stack 简历草稿，而不是只修改 frontend 关键词。
6. 用户通过 Agent 或表单调整，选择模板、排版并导出 PDF。
7. 原 frontend 简历保持不变；已确认的经历可供后续其他简历复用。

### 场景 B：没有现成简历，也没有具体 JD

1. 用户点击「创建简历」，说明希望创建一份 frontend 简历。
2. 通过对话梳理相关经历，不必先填写完整资料库。
3. 核对并保存 Agent 整理的事实，生成岗位方向通用版。
4. 在工作台继续编辑并导出，不必提供某家公司的 JD。

### 场景 C：不想使用 Agent，或者中途改用表单

1. 用户直接选择手动编辑视图填写简历，无需先完成对话。
2. 表单操作反映在同一份简历预览中。
3. 如需 AI 帮助，切换到 Agent 视图，基于当前内容提出修改要求。
4. Agent 展示修改建议，用户决定是否应用。
5. 再切回表单时，保留已经确认的修改，不产生另一份内容副本。

以上是典型旅程，不要求所有用户必须先建经历库再提供岗位。首次使用的引导细节尚待设计。

## 9. 从共识提炼的行为验收基线

这些是后续设计、实现与测试应保护的用户行为，不表示已经通过验证。

| 情境 | 预期结果 |
| --- | --- |
| 在同一个创建入口发送岗位方向、JD 或 URL | 能表达对应目标，不要求用户先选择三种创建类型；URL 异常流程仍待确认 |
| 创建另一份简历时已有相关个人事实 | 复用已确认事实，不要求重复复制教育、工作等内容 |
| JD 要求某项技能，但经历库没有记录 | 可以追问，不能把岗位要求写成用户已经具备的能力 |
| 用户核对 Agent 提取的事实 | 可以修改后集中确认；未确认的推断不作为事实使用 |
| Agent 修改已有简历 | 用户看到拟修改内容，并能接受或拒绝；拒绝不改变原内容 |
| 待确认建议产生后，用户手动改了同一段 | 旧建议不能覆盖新内容，需要基于最新内容重新提出建议 |
| 用户在 Agent 与表单视图间切换 | 简历和聊天内容保留，Agent 后续操作基于最新简历 |
| 用户只调整某份简历的措辞 | 不自动更新经历库，也不修改其他简历 |
| 用户确认向经历库补充事实 | 后续生成可以复用，但已生成的其他简历不自动变化 |
| 用户不使用 chat | 仍可通过表单编辑，并完成产品内排版与 PDF 导出 |
