# 我的个人开发流程

> 供自己操作，不是 agent 的必读规范。按当前阶段发送提示词，不要一次发送整个流程。下面沿用 Pi 的 `/skill:名称` 写法；在其他 agent 中通过它的技能选择入口调用同名 skill。

**`grill-me` 澄清需求 → `to-spec` 固定约定 → `to-tickets` 拆任务 → 选择一个任务 → `tdd` 实现 → 普通评审与验收 → 更新交接。**

我负责决定目标、范围、重要取舍和是否验收；agent 负责查证代码事实、提出方案、实施和给出验证证据。确认一项决定后复用它，不在每个步骤重新访谈。

## 0. 准备与选择流程

- 从仓库根目录启动；在技能列表中确认 `grill-me`、`grilling`、`to-spec`、`to-tickets`、`tdd`、`vercel-react-best-practices` 可用。
- `grill-me` 是入口，`grilling` 是它调用的访谈能力，不需要分别运行。工作流已经初始化，不需要 setup skill。
- 新功能或存在重要业务取舍的需求走完整流程。小而明确的文案、样式、配置修改可直接实施并验证；已明确的 bug 可直接进入失败回归测试和修复。
- React / Next.js 工作配合 `vercel-react-best-practices`，它是实现与检查时的参考，不是额外的人工审批阶段。
- 不可用的技能或工具应如实说明，不声称已经运行，也不自动安装。TDD 提及的设计、评审步骤使用项目现有规则，不依赖另装 design / review skill。

文件约定见 [tracker conventions](agents/issue-tracker.md) 和 [domain documentation](agents/domain.md)：

```text
docs/
├── plans/<feature-slug>/
│   ├── spec.md                 这次功能约定做什么、不做什么
│   └── issues/
│       ├── 01-<ticket>.md      一个可独立验证的任务 / Delivery Slice
│       └── 02-<ticket>.md
├── agents/                    工作流的存放、状态和资料导航约定
├── designs/                   当前实现的核心设计
└── handoff.md                 当前进度、验证、阻塞和下一步
```

只在确实需要时创建功能文件；不为小修改预建规格和任务。任务文件拥有状态，handoff 只做摘要和链接，不复制整份任务清单。

## 1. 用 grill-me 想清楚问题

```text
/skill:grill-me 我要做：<需求描述>。
先澄清目标、非目标、关键业务规则、重要失败场景和验收标准。
聚焦影响当前需求的决定，给出建议；能从代码确认的事实自行检查。
目标、范围和验收明确后停止追问，只总结已确认决定和真正未决的问题。
这一步只讨论，不写业务代码、不安装依赖。
```

我确认需求边界后再进入规格阶段。这里的产出是共同理解，不是一次性决定后续所有功能。

## 2. 用 to-spec 固定约定

```text
/skill:to-spec 将刚才确认的需求整理为 docs/plans/<feature-slug>/spec.md。
复用已确认决定，不重新开启需求访谈，也不扩展功能范围。
记录问题、用户行为、范围与非目标、关键职责和数据边界、失败处理、验收与测试思路。
测试选择遵循项目的风险与成本原则；已确认的测试边界直接复用。
如存在影响规格成立的未决问题，单独指出，不替我作决定。
只写本地规格，不实现；完成后等我确认规格。
```

规格回答“这次做什么、怎样才算正确”。它不需要变成逐文件编码方案，也不重复建立另一套长期设计文档。

## 3. 用 to-tickets 拆成可交付任务

```text
/skill:to-tickets 根据已确认的 docs/plans/<feature-slug>/spec.md 拆分任务。
每个任务交付一个能独立演示或验证的完整行为，不机械拆成数据库、后端、前端。
写清交付结果、范围与非目标、Blocked by、验收标准和验证方式。
先展示任务粒度和依赖，等我确认后写入 docs/plans/<feature-slug>/issues/，每个任务一份文件。
只拆任务，不实现、不创建远程 issue。
```

我确认拆分后，选择一个依赖已完成的任务。**一个 ticket 就是一个 Delivery Slice**，不再额外维护一份重复的 slices 计划。任务可开始不代表 agent 可以自行开始。

## 4. 选择一个任务，用 TDD 实现

```text
/skill:tdd 本次只实现 docs/plans/<feature-slug>/issues/<NN>-<ticket>.md。
先读取规格和任务，核对 Git 状态、相关代码及已有测试，保留无关改动。
列出需要验证的公开行为、测试边界和关键风险，优先复用已有测试。
测试边界未确认时先给出建议并等我确认；如果前面已确认，直接复用，不重复询问。
确认后按“一个失败测试 → 最小实现 → 测试通过”逐步完成当前任务。
React / Next.js 改动同时参考 vercel-react-best-practices。
只做当前任务，运行相关检查；不开始下一个任务，不提交或推送。
```

如果需要先确认测试边界，我确认后只需发送：

```text
测试边界确认，开始实现当前任务。在约定范围内连续完成，不必每个测试再次询问。
仅在范围、重要风险或方案约束实质变化时重新确认。
```

先保护正常路径和最重要的失败路径；测试按行为与风险组织，不按生产文件数量铺开。普通框架接线和不改变行为的结构调整按项目规则验证，不强行为每处改动补测试。

## 5. 普通评审与实际验收

实现完成后，以普通请求发起评审：

```text
Review 当前任务的全部改动，包括相关已提交、暂存、未暂存和未跟踪文件，并说明比较范围。
对照规格和任务，检查遗漏、越界实现、行为、安全、事务和回归风险。
先给出发现与依据，不自动修复或重构，不为评审创建提交。
```

我选择需要修复的问题，授权修复并重跑受影响检查。然后按任务验收标准实际使用结果；有重要失败路径时验证失败表现与恢复方式。自动化通过不等于真实 Google 登录、PDF 或完整用户流程已验证，应区分证据。

## 6. 更新状态与交接，再决定下一步

```text
核对最终 diff 和实际验证结果，区分新增失败、旧问题与未验证部分。
更新当前任务的 Status 和验收结果；完成验收才标记 done。
需要人工验收但尚未完成时，保持 in-progress，并注明待确认内容。
核心决策或行为变化时更新对应规格和受影响的现有设计。
简短更新 docs/handoff.md，记录状态、验证、阻塞和下一步，链接相关规格与任务。
到此停止，不自动开始下一个任务，不 commit、push、部署或迁移。
```

我决定继续哪个任务，或明确授权提交、推送等交付操作。一次完整流程可以产生多个 ticket；每个 ticket 都分别经历实现、评审与验收，不需要重新访谈整个功能。

## 换 session 继续

```text
先读取 docs/handoff.md 和关联规格、当前任务，核对 Git 状态与实际代码。
总结当前任务、已确认的范围和测试边界、验证结果、阻塞与下一步。
复用已有决定，不重开整套访谈；记录与代码不一致时先指出。
handoff 为空时不要推断进度。先报告状态，等我指定本次要继续的任务。
```
