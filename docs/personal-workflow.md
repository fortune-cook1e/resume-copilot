# 我的 Pi 开发流程

> 仅供自己操作，不是 agent 的必读规范。按步骤发送提示词，不要一次发送整个流程。

**需求访谈 → 确认方案与当前 slice → 确认测试边界 → 实现 → 评审与交接。**

## 0. 准备

- 从仓库根目录启动 Pi；新增 skill 后输入 `/reload`，通过 `/skill:` 补全确认命令可用。
- 当前 `grill-me` 只是调用 `grilling` 的入口，仓库尚未包含后者。补齐后使用下面的命令；暂不补齐时，去掉 `/skill:grill-me`，以普通对话完成访谈，不声称执行了原版 skill。
- 小而明确的文案、样式、配置调整：直接说明范围并要求验证，不强制走访谈、方案和 TDD。重要业务规则与 bug 回归使用 TDD。

## 1. 澄清需求，不实现

```text
/skill:grill-me 我要做：<需求描述>。
先澄清目标、非目标、关键业务规则、失败场景和验收标准。
每次只问一个影响决策的问题，并给出建议；代码能确认的事实自行检查。
边界明确后停止追问。只做需求访谈，不写代码、不安装依赖。
如果所需技能或工具不可用，先说明，不假装已经运行。
```

## 2. 写方案，拆 Delivery Slices

需求确认后发送；小需求可跳过独立方案文档。

```text
根据已确认的需求，整理设计方案和 Delivery Slices，写入 docs/ 下的对应方案文档。
记录关键决策、职责与数据边界、重要失败路径和未决问题。
每个 slice 写明交付结果、范围与非目标、依赖、验收与验证方式、状态。
优先按可验证的完整行为拆分，不机械拆成数据库、后端、前端三个阶段。
只写方案，不实现；等我确认方案并选择本次 slice。
```

## 3. 选定 slice，确认测试边界

```text
/skill:tdd 方案已确认，本次只做 <方案路径中的 Slice N>。
先列出需要验证的公开行为、测试边界和关键风险，检查已有测试能否复用。
先覆盖正常路径和最重要的失败路径，不按生产文件逐个建立测试文件。
先不要写测试或实现，等我确认边界；缺少必要技能或工具时先说明。
```

## 4. 授权实现当前 slice

```text
测试边界确认，开始实现。
逐条执行：失败测试 → 最小实现 → 测试通过，不批量写完所有测试再实现。
在已确认范围内连续完成，不需要每个测试都再次询问。
出现范围变化、重要新风险或方案冲突时再停下来确认。
只做当前 slice，运行相关检查；不夹带架构重构，不开始下一阶段，不提交。
```

## 5. 评审，再收尾

```text
Review 当前 slice 的全部改动，包括未跟踪文件。
优先检查行为、安全、事务和回归风险；先给出发现，不自动修复或重构。
```

确认需要修复的问题，修复并验证后发送：

```text
核对最终 diff 和验证结果，区分新增失败、旧问题与未验证部分。
更新方案中的 slice 状态；核心决策变化时同步方案和受影响的 slices。
简短更新 docs/handoff.md，记录当前状态、验证、阻塞与下一步，并链接方案。
不要自动开始下一阶段，不 commit、push、部署或迁移。
```

当前流程准备阶段的 handoff 保持空模板；进入实际交付阶段后再填写。

## 按需：架构专项评审

不是每个 slice 的必经步骤；出现实际架构摩擦时再使用，先确认技能依赖可用。

```text
/skill:improve-codebase-architecture 只评审 <明确范围>。
给出实际问题和取舍，不修改业务代码；等我选择问题、确认方案后再重构。
缺少所需技能或工具时先说明，不自动安装。
```

## 换 session 继续

```text
先读取 docs/handoff.md 和关联方案，核对 Git 状态与实际代码。
总结当前 slice、已验证结果和待确认事项；handoff 为空时不要推断进度。
先不要开始新的实现，等我确认本次范围。
```
