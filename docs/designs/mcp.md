## 1. Goal and agreed scope

The current backend validation outcome is **connect, explicitly authorize, call a minimal protected tool, and revoke**. The target user entry is installation from a shareable Git marketplace, not manually adding an MCP URL. The next smallest slice packages the existing minimal connection for local plugin-install validation; it is not the experience-to-resume collaboration flow yet.

- Run a remote-style Streamable HTTP MCP endpoint locally for initial acceptance, not a stdio subprocess. Public HTTPS deployment is a separate task.
- Target user flow: add a Git marketplace source, install Resume Copilot from its Plugins Directory, then complete platform browser login and explicit Allow/Cancel before using the tool. Manually adding a server URL is only a local protocol diagnostic. Do not require manual client ID, callback, Bearer token, Cookies or client secret configuration. Real plugin/desktop acceptance is pending.
- Use `@better-auth/cimd` client metadata discovery (ChatGPT-hosted `https://chatgpt.com/oauth/codex/.../client.json` documents) with a strict URL allowlist and the official Node DNS-pinned, TLS-validated, no-redirect fetcher. Do not enable open dynamic client registration. Client IDs are identifiers, not proof of a physical device.
- Retain Google-only platform login. An authenticated browser user must separately approve Codex access; do not link Codex and platform accounts by email.
- Expose only `get_connection_status`, returning a minimal platform account identifier, display name, and granted scope information. Exclude email, credentials, experience records, and resume content. Exact field names and scope identifiers are implementation contracts to settle during A0/A, not existing APIs.
- The consent page shows the current platform account and requested permission, with explicit allow/cancel actions. Cancel must not create a usable grant.
- Every completed new authorization creates an independent connection. Normal token refresh does not create another connection. Do not silently reuse prior consent to create new grants or expand permissions.
- Provide a simple authenticated connection list showing authorization/expiry information and individual revocation controls. Client names and timestamps do not establish which physical device owns a connection.
- Future experience/resume permissions require new explicit consent; this connection does not automatically inherit them.

Out of scope for the next packaging slice: experience library, resume migration to NestJS, resume creation or modification tools, proposal/version-control workflows, PDF changes, stored JD/chat, in-product agents, public deployment, Git publication and OpenAI directory submission. These remain later slices under the [product definition](../product.md).

## 2. Separate responsibilities, one application

MCP does not require Better Auth or a separate service. This project selects the Better Auth ecosystem to reuse platform identity and its MCP-specific authorization integration. Preserve Google-only login and browser-session behavior while coordinating the dependency upgrade required by `@better-auth/mcp`.

Register `mcp()` on the existing authoritative Better Auth instance: it is that instance's OAuth Provider, so do **not** also register `oauthProvider()` or create a second authorization server. `@better-auth/cimd` adds client discovery to the same provider (not a second OAuth server). The official MCP SDK still owns tool registration, invocation, and transport; the auth plugin does not implement the business tools.

| Owner | Responsibility |
| --- | --- |
| `apps/api/src/auth/` | The authoritative Better Auth instance: Google login, browser sessions, trusted platform identity, and `mcp()` authorization plugin configuration |
| `apps/api/src/oauth/` | Connection state repository and lifetime service; future connection management, not another OAuth Provider instance or a hand-written token protocol |
| `apps/api/src/mcp/` | MCP transport, tool registration, validated tool inputs/outputs, use of the OAuth module's trusted authorization context |
| Future business modules | Experience/resume rules, ownership checks, transactions; shared by HTTP and MCP adapters |
| Existing database module | Connection lifecycle and API-owned schemas/migrations; business persistence stays with its owning module |
| Web | Consent and connection-management UI, using platform browser authentication |
| `packages/contracts` | Minimal public schemas/types when introduced; no provider records, database entities, or framework types |

All API modules run in the same NestJS process and deployment. Do not add an application workspace, authorization microservice, Redis, queue, or another user-login system. The protocol provider may own its internal OAuth sessions/interactions; these must not become an alternative source of platform user identity.

MCP tools call exported business services rather than duplicating business rules or importing another application's internals. In this slice there are no resume tools, so do not precreate future business modules.

A plugin package and marketplace catalog describe how the desktop finds this same MCP service; they are not another API, auth server, or deployment. The official [plugin packaging guide](https://developers.openai.com/plugins/build/plugins) distinguishes portable `plugin.json`/`mcp.json` from the OpenAI compatibility overlay and registered MCP app mapping. The first skeleton uses only portable manifests; confirm whether this desktop install surface requires a separately registered `plugin_asdk_app...` mapping rather than inventing an ID. The [plugin auth guide](https://developers.openai.com/plugins/build/auth) lists ChatGPT CIMD identities at `https://chatgpt.com/oauth/client.json` or `/oauth/{callback_id}/client.json`, whereas the current local provider only allows `/oauth/codex/...`; browser authorization for an installed plugin has **not** passed. Verify the actual identity before making a separately scoped auth change. For local installation the URL may target the same-machine loopback trial; sharing the marketplace via Git does not deploy that server or let other users reach a localhost URL. External use requires a separately authorized stable HTTPS endpoint and completion of connection management and security acceptance.

## 3. Data flow and boundaries

1. ChatGPT desktop connects to the local MCP HTTP endpoint and discovers the relevant authorization metadata.
2. ChatGPT desktop starts an authorization-code flow with S256 PKCE as a public client. The library owns OAuth protocol validation, code exchange, and token issuance; do not implement the protocol from scratch.
3. The browser reaches the platform interaction/consent flow. If needed, use the existing Better Auth Google login. The server establishes the current user; client-supplied account IDs cannot select an identity.
4. The user reviews the current account and minimal permission, then allows or cancels. On approval, bind a new connection/grant to that account. A stale interaction must not silently bind consent to a different browser account.
5. ChatGPT desktop exchanges the authorization code for its own credentials. The platform browser Cookie is never a Codex credential. Use registered, validated callbacks rather than arbitrary return URLs.
6. Each protected MCP request validates its access token, intended resource/audience, scope, and the current grant state before returning the minimal tool result.
7. Connection management uses the current platform browser session and owner-scoped operations. Revoking a connection invalidates subsequent tool requests and refresh attempts for that grant only.

Keep three identities distinct: the platform user, the OAuth client registration, and the individual connection/grant. Two authorizations from the same platform user and public client ID still need independent grants.

### Native protocols and HTTP security

- OAuth endpoints retain native discovery, redirects, token/error responses, and headers; MCP retains its protocol responses. Neither is wrapped in the business `{ data, error }` envelope. Ordinary connection-management business APIs follow the [HTTP response contract](http-response.md).
- Existing `/api/auth/*` browser write protection remains in place. Protocol-specific token requests from a desktop client cannot simply inherit the blanket browser Origin requirement in `main.ts`; mount and protect those boundaries explicitly rather than disabling CSRF globally.
- Browser consent/revocation writes need CSRF/Origin protection and a verified platform session. Desktop protocol requests need their OAuth-specific validation. Do not assume all requests carry a browser Origin or enable blanket CORS.
- Local listeners, Host/Origin checks, discovery URLs, callback validation, and resource identifiers must agree. Permit HTTP only for the intended loopback development flow; production remains HTTPS-only and separately scoped.
- Logs must not contain authorization parameters/codes, tokens, Cookies, request/response bodies, or private user data. Database/service failures fail closed with safe protocol-appropriate errors, not false authorization success.

Final endpoint paths, middleware order, registered callback settings, client configuration syntax, and SDK protocol-version selection must be verified against the actual desktop version in A0/A. Do not publish speculative executable setup commands as tested instructions.

## 4. Connection lifecycle invariants

| Event / property | Required behavior |
| --- | --- |
| Access token lifetime | At most 15 minutes, never extending usable access beyond grant expiry |
| Grant lifetime | Absolute 30-day maximum from authorization; refresh never resets that deadline |
| Refresh | Automatic while the grant is valid; rotate credentials safely without creating another connection |
| Grant expiry | Access and refresh fail; require a new explicit authorization through the platform login/consent flow |
| Browser sign-out / expiry | Does not revoke or expire an already-authorized MCP connection |
| New authorization | Creates an independent grant, including for the same user/client pair |
| Successful revocation | Newly checked tool requests and refresh attempts fail immediately; do not wait for access-token expiry |
| Other connections | Remain usable when one grant is revoked; replay handling must not accidentally revoke every grant for the user/client pair |
| Revocation failure | UI does not claim success; offer a safe retry |
| Previously authorized work/data | Revocation cannot retract data already delivered or roll back requests authorized before revocation |

Validate both token and current connection/grant state on each protected request. The documented `@better-auth/mcp` setup uses the JWT plugin and signing keys; signature/expiry checks alone do **not** establish immediate revocation or absolute grant expiry. A0 must verify the supported server-side state-validation path and token-to-connection association; do not assume the default MCP auth helper enforces these product rules. Do not force the former opaque-token design onto the new stack or introduce a cache that delays revocation.

The persistent connection/grant state is the authority for absolute expiry and revocation. A refresh racing with revocation must not produce usable access after revocation commits. Verify atomic code/refresh consumption, transaction behavior, and connection isolation through the Better Auth provider and existing Drizzle/PostgreSQL integration. Do not build an `oidc-provider` adapter or assume that a provider consent record keyed by user/client represents an independent connection.

Prefer supported configuration and extension points; any additional application-owned connection state must be justified by these invariants. Exact persistence schemas and token-material protection depend on the selected compatible Better Auth/plugin versions. The eight provider/JWT models were added in migration `0002_mcp_oauth_provider.sql`. Migrations 0002/0003 were applied to the isolated test database and, after separate approval, to local development. No reset or production migration was performed. Expired/revoked record retention and cleanup details remain implementation decisions to resolve before adding cleanup behavior; do not invent a retention promise or background service in this slice.

### Implemented absolute-expiry integration

- `oauth_connection` holds an independent connection ID, platform user/client IDs, approved scopes, original authorization timestamp, fixed expiry, and nullable revocation timestamp. It has no browser-session FK. Migration 0003 adds this table with owner/client FKs and a database check enforcing exactly 720 hours between authorization and expiry. It was applied to the test database, then separately approved and applied to local development.
- `postLogin.consentReferenceId` allocates a server-generated UUID through Better Auth's public `defineRequestState`. It is stable across repeated callbacks inside one consent request, but fresh for every new request. An authorization request cannot silently find a prior consent. Declaring the already-used `@better-auth/core` 1.7.5 as a direct API dependency permits this public context API without transitive/deep imports or global mutable request state.
- After the provider validates and consumes an authorization code, its access-claim extension reads the matching approved provider consent (reference/user/client) and creates the platform record once. The deadline uses consent `createdAt`, not exchange time. An insert conflict never overwrites original state. Refresh cannot create a missing connection. The provider carries `referenceId` through its code and refresh records; signed access tokens receive `mcp_connection_id`.
- Issuance checks persisted owner, client, approved scopes, expiry and revocation. A companion plugin's public before-hook also checks connection state before refresh processing, because the provider can return a cached rotation response without rerunning claims extensions. The explicit `storeTokens.hash` configuration and unprefixed/unwrapped refresh format let that hook look up only hashed token material through the repository, without importing provider internals or replacing token validation/rotation.
- `createConnectionProtectedHandler` delegates signature, issuer, audience and required-scope validation to the official MCP helper, then checks connection state on every request. A JWT may retain its normal 15-minute `exp` beyond the connection deadline; it is **not usable** beyond that deadline. Inactive state returns native 401 with a bearer challenge; connection-store failures return a safe 503, never authorize access. No connection-state cache was added.
- Each insertion is atomic and idempotent by reference. An owner-scoped internal revoke operation makes existing signed access and refresh credentials unusable; browser sign-out/expiry does not revoke an MCP grant. An ordinary stale-refresh replay after the retry window is intercepted and revokes only its connection. An authenticated revocation endpoint, connection UI and cleanup job are not exposed. The local trial exposes only `get_connection_status` when explicitly enabled and migrated. Enable only for the explicitly accepted local trial; do not expose it to a network or treat it as production-ready.

## 5. Selected stack and A0 evidence

**Selected direction: Better Auth + `@better-auth/mcp` + the official MCP SDK, inside the existing NestJS application. Do not introduce `oidc-provider`.** The earlier standalone-provider recommendation is superseded: source-level differences did not demonstrate that introducing another authorization framework would be simpler than configuring/extending the existing ecosystem. This selection is not a claim that every product invariant works out of the box.

The preliminary review checked repository code, installed Better Auth 1.4.18 source, official documentation, npm metadata, and integrity-checked candidate package archives downloaded only to temporary review directories. The standalone `@better-auth/mcp` documentation/metadata and its underlying OAuth Provider source were inspected before implementation. ### Test boundaries

- Existing tests protect Google login, platform sessions, sign-out and owned resume access, not MCP OAuth/grant invariants. Use failing tests first for new security, lifecycle, and transaction behavior.
- `apps/api/test/mcp-authorization.test.mts` groups provider authorization behavior against real PostgreSQL. It seeds isolated identities and a pre-registered public client for legacy lifecycle checks, then authorizes a ChatGPT-style metadata client without preregistration via a controlled external fetch boundary. Both use the public Fetch handler; Google login remains covered by existing tests. API test files run sequentially because the existing auth suite truncates shared fixture tables. Resource checks use the official MCP verifier against the real provider's JWKS served on an ephemeral loopback HTTP listener. The additional HTTP test exercises the mounted NestJS adapter, discovery, native refresh and SDK tool calls. It does not verify the full Web proxy/browser consent redirect or a real ChatGPT desktop.
- Use real HTTP/provider boundaries and the isolated database where token binding, grant state, consumption, or races matter. Cover wrong PKCE/callback/resource/scope, expired/replayed codes/tokens, owner isolation, and the distinct lifecycle invariants above without repeating every case across layers.
- In A, add low-cost Web behavior coverage where consent/revocation failure or account changes introduce a distinct risk. Do not scaffold browser E2E for the unimplemented flow during A0.
- Automated time-controlled tests must verify refresh and absolute expiry. Actual ChatGPT desktop authorization/refresh/revocation remains a separate interoperability check; an SDK client or curl does not establish desktop compatibility.
- After authorized code/dependency changes, run relevant tests, typecheck, build, and workspace lint (`pnpm lint` includes nested configs). Run covered browser journeys separately with `pnpm test:e2e` if available; otherwise explicitly report manual-only coverage. Keep historical lint failures and Auth C browser acceptance gaps visible.
- Automated database integration uses only the isolated test database, never development or production data. Each database migration required explicit target-specific approval; production remains unauthorized.

### Rollback / stop conditions

Keep the existing Better Auth instance and login routes authoritative. If upgrade compatibility, grant isolation, or desktop OAuth interoperability fails, stop and report the failed requirement; do not weaken PKCE, callback, Origin, expiry, or revocation checks. Use supported configuration/extension points rather than patching library internals. Do not silently switch to `oidc-provider`, enable a second provider, or change product invariants to make tests pass; any material architecture change requires a new decision. Provider routes and UI exposure can be disabled independently of platform login; database cleanup and dependency rollback require a reviewed, non-destructive plan.
